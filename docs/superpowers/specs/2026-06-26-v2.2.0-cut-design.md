## 2. Cross-cutting NFRs (apply to every run in the cut)

These are requirements on SP-II's runs especially, but stated here as the cut-wide contract:

- **N1 · No wasted progress (checkpointing + resume).** Every run checkpoints at the
  per-(detector × language-shard) granularity and is fully resumable. A crash, a killed process, or a closed
  lid re-pays only the in-flight shard, never finished work. (The existing cloud runner already skips any
  detector that wrote `baseline_results.json`; SP-II extends this to per-(provider,lang) and to the local lane.)
- **N2 · Detailed summaries.** Every run emits (a) a live progress log and (b) a structured final report:
  per-detector / per-language / per-script F2 with Wilson CIs, record-error counts, wall-clock, cost actuals
  (cloud), and a human-readable summary block.
- **N3 · Laptop-friendly.** Anything that runs on the laptop runs at low priority (`nice`/`ionice`), under
  `caffeinate -i` (survives idle sleep / lid-close), with capped concurrency so it never saturates CPU/GPU while
  the PI works, and is resumable so it can be paused/killed anytime.
- **N4 · Run placement.** Heavy multilingual local census + cloud → **VM**. Light steps (smoke, B-4 sanity,
  McNemar gliner arm, `coverage_decomposition`, version/docs/mint prep) → **laptop** under N3.

SP-I is a minutes-scale laptop job, so N1's heavy machinery is not needed here; SP-I satisfies N2 via the W1
change report + the W2 validation report, and N3 trivially (short, single-process).

- **Only PERSON_NAME + name-derived EMAIL_ADDRESS values change** in Thai records; all other span types and all

- **Paper substrate (EX00) untouched:** the migration touches **nothing** under the EX00-frozen paths
  (`results/tier-a/`, `results/per-record/`); its report goes to `results/` root → `write_manifest.py
  --frozen-check` stays green with **no EX00 regeneration**.
- **Offset validity preserved:** for every rewritten span, `text[start:end] == annotation["text"]` (0 offset
  errors corpus-wide via `validate.py`), and every later span in the same record is shifted by the exact net delta.

## 5. SP-I — W1 design: the Thai-name upgrade (approach γ′ — surgical transliteration, PI-approved)

**Revision note (2026-06-26, post data-investigation):** the originally-recommended **γ** (rewrite the
PERSON_NAME span only) is **incorrect** — the EMAIL_ADDRESS local part is **derived from the person name**
(`generate_records.py:352` `email(person_name)` → `f"{first}.{last}{N}"`, lowercased), and the 2C precedent
(el/bn/he) produces **native-script emails** (e.g. Greek `Παναγιώτης Βασιλείου` → `παναγιώτης.βασιλείου61@…`).
A PERSON_NAME-only patch would ship Thai-script names with romanized emails — a realism regression and
inconsistent with 2C. The PI chose **γ′ (surgical, in this cut)**.

Approaches weighed:
- **α — Full deterministic rebuild** — *rejected:* entangled with the fill→merge→enrich layering + the 1,000
  non-deterministic AI-era records; needs pre-fill-base reconstruction; re-opens the `declare-head`/`from-metadata`
  trap.
- **β — Regenerate Thai fill only** — *rejected:* the fill's running counter shares incidental positives across
  cells; fragile.
- **γ′ — Surgical in-place transliteration migration (CHOSEN)** — extends γ to rewrite **PERSON_NAME _and_ its
  derived EMAIL_ADDRESS** via a deterministic romanized→Thai-script **transliteration map**, in the proven
  `scripts/v2_0_0_to_v2_1_0.py` / `honesty.py` streaming-migration mould.

**Why a transliteration map beats a random native pool (the key design choice):** instead of drawing a *random*
native name (which would decouple the name from its derived email and force per-record cluster reconstruction),
γ′ maps each of the **28 existing romanized Thai names** (16 first + 12 last in `FIRST_NAMES_TH`/`LAST_NAMES_TH`)
to a fixed Thai-script spelling. Because the same romanized string always maps to the same Thai string:
- **Cluster consistency is free** — every variant of a person ("Prayut Rattanakorn" / "Dr. Rattanakorn" /
  "Prayut") transliterates consistently without reconstructing `cluster_id` groups.
- **Email-derivation consistency is free** — `pichit.srisai31@…` → `พิชิต.ศรีสาย31@…` by transliterating the
  same name parts (number suffix + domain preserved).
- **No RNG / no seeding** — the migration is a pure deterministic lookup (simpler, more auditable than
  seed-drawing), trivially idempotent (Thai-script input has no romanized keys to map → no-op).
- **Base + fill records handled uniformly** — both the 40,845 fill and 277 `synthetic` base Thai records drew
  from the same 28 romanized names, so the map covers both with no special-casing.

**Ground-truth that makes γ′ tractable (verified):** of 41,122 Thai records, **41,051 (99.83%)** have exactly
one `full_name` PERSON_NAME; mention-variant distribution is full_name 41,039 / None 157 / formal 30 /
first_name 19 (no last_name / first_last_initial); only **71** records are multi-PERSON_NAME; **40,984 / 41,111
(99.7%)** emails match a `full_name` PERSON_NAME's `first.last`; **0** records have an email without a PERSON_NAME.

**γ′ mechanism (per Thai record):**
1. **PERSON_NAME spans (variant-agnostic, token-wise)** — split the span text into whitespace tokens; for each
   token, if `token.lower()` is in the map, replace with its Thai form, else leave it unchanged. This handles every
   variant with no special-casing: `full_name` "Pichit Srisai" → "พิชิต ศรีสาย"; `formal` "Dr. Rattanakorn" →
   "Dr. รัตนกร" (honorific left, as el/bn/he render); `first_name` "Prayut" → "ประยุทธ์". A span with **no** mapped
   token (already Thai, or only honorifics/initials) is left unchanged and counted in the report.
2. **EMAIL_ADDRESS spans (segment-wise)** — split `local@domain`; split `local` on `.`; for each segment strip a
   trailing digit run, map the alpha part if `alpha.lower()` is in the map (reattach the digits), else leave the
   segment; rejoin. So `pichit.srisai31@dom` → `พิชิต.ศรีสาย31@dom`. A local part with no mapped segment is left
   unchanged and flagged.
3. **Text + offsets** — collect the (start, end, new_value) edits for the record's changed PERSON_NAME + EMAIL
   spans; rebuild `record["text"]` left-to-right; recompute every span's `start`/`end` via a cumulative delta (edited
   spans get `new_start + len(new_value)`; later non-edited spans shift by the net delta of edits before them);
   re-assert `text[start:end] == new_value` for every edited span.
4. **Naturally idempotent** — a re-run finds no mapped tokens in already-Thai records → 0 edits → byte-identical
   output. **No marker field is added**, so the only bytes that change in a Thai record are the PERSON_NAME + EMAIL
   span values (and the offsets that follow them).
5. Records with `language != "th"` pass through byte-identical; **do not** re-stamp `version`/`schema_version`
   (content stays 2.1.0 until SP-III).

**Scope:** PERSON_NAME + name-derived EMAIL_ADDRESS only. USERNAME is `{word}_{num}` (`generate_records.py:434`),
**not** name-derived → untouched. ORGANIZATION_NAME / LOCATION_NAME / MEDICATION_NAME / PROCEDURE_NAME draw from
non-person pools → untouched (mirrors el/bn/he, which localized person identity only). The report audits all
untouched name-bearing types so the decision is reviewable.

**Edge-case handling (~280 records, 0.7%):** the multi-name (71) + non-full_name (≈206) records are handled by
the same per-span variant logic above; the migration report **lists every edge-case record id** (multi-PERSON_NAME,
formal/first_name/None variant, or any unmatched name/email) so the PI can eyeball the long tail. A span whose
name/email cannot be mapped is left unchanged and counted, never silently mangled.

**Thai spellings:** `FIRST_NAMES_TH_NATIVE` / `LAST_NAMES_TH_NATIVE` are the Thai-script spellings of the 28
existing romanized names, **index-parallel** to `FIRST_NAMES_TH`/`LAST_NAMES_TH` (so the map is
`dict(zip(romanized, native))`). `NAME_DB["th"]` is re-pointed to the native lists so future generation produces
Thai-script names directly. The spellings are standard transliterations of common Thai names; **the plan flags
them for a quick PI/Thai-speaker spelling check** before the freeze (they are real-name renderings and accuracy
matters for realism).

## 9. SP-I — Risks & mitigations

- **Offset miscomputation** (multiple edits per record — PERSON_NAME + EMAIL — with Thai names a different byte/char
  length) → the migration recomputes offsets left-to-right with a running delta and re-asserts
  `text[start:end]==new_value` per edited span; unit-tested across single/multi-edit cases (§8); the W2 gate
  re-asserts offset validity corpus-wide via `validate.py`.
- **Email not actually name-derived** (random local part, or a name with ≠2 parts) → the migration only rewrites an
  email whose `(a,b)` both map; anything else is left unchanged and flagged in the report.
- **Inaccurate Thai spellings** → the native lists get a PI/Thai-speaker spelling check before the freeze (§6.1).
- **Accidental substrate drift** (a stray change to a non-Thai record or to an EX00-frozen path) → caught by the
  byte-identical pass-through behavior + the W2 `--frozen-check` gate + the reviewed diff.
- **Future silent revert** (a later rebuild regenerating romanized Thai) → mitigated by re-pointing `NAME_DB["th"]`
  to the native lists + the generator parity test, so generator and corpus agree.
